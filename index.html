The bet

The thesis

Kitchen robotics is really three problems. The defensible value lives in the last two — so we build those first, with no hardware.

1 · Robot control

Move the arm, pick, stir, pour. A solved-ish, commodity layer with mature open-source tooling.

2 · Cooking intelligence

Recognise state — onions golden, oil too hot, curry reducing. Cooking is fundamentally a state-recognition problem.

3 · Recipe knowledge

Turn “make butter chicken” into ordered, executable steps. Structured culinary knowledge.

🧠
Operating principle — software-first, hardware-last. The biggest mistake is buying hardware before you know what software it should run. The first thing to prove is not robotics; it’s that our software can understand and execute cooking procedures.

Guard-rails we’ve already chosen

  • Build the robotics layer in Python (ROS2 · MoveIt2 · OpenCV), not Rust. Rust only for the niche vector-index layer.
  • Use an induction cooktop, not gas — digital, API-controllable, safer to automate.
  • No knife / cutting work early — it needs force feedback, precision and safety systems. Start with pick · move · pour · stir.
  • First real milestone is tiny on purpose: “robot adds onions to a hot pan and stirs for 60 seconds.” If that works, perception + planning + execution are all proven.

The arc

Phased roadmap

Each phase de-risks the next. We only buy an arm once the software brain is real.

Phase 0 · the only thing it must prove

Kitchen OS v0.1 — scope

A command-line pipeline that turns a recipe URL or pasted text into a validated, machine-executable recipe JSON. No robot, no vision, no scraping at scale.

🎯
The one hypothesis: Can software reliably decompose human cooking instructions into structured, executable steps — including the “how do I know this step is done?” cues? If yes, the simulator → vision → arm phases have a foundation. If no, we learned it in ~2 weeks instead of after buying an arm.

The core artifact — the recipe schema

This is 80% of the value. It’s deliberately robot-ready: every step carries a completion condition that is either timed or state, and each state-based step names an observable — exactly what the Phase-2 vision system will later detect. So v0.1 output is never throwaway.

action vocabulary

The “action space” — small and extensible:

add heat saute stir simmer boil fry flip pour transfer wait season knead rest garnish serve

completion.type

  • timed → duration_s
  • state → cue + observable (every state step must name an observable)

Milestones (~2 weeks)

  • Week 1 — the spine. schema.py + 5 gold recipes + extraction prompt + a CLI doing URL→text→Claude→validated JSON for one recipe end to end. now
  • Week 2 — trust it. Validation + confidence flags + review loop; batch-extract 20–30 recipes; eval/score.py vs gold; iterate the prompt. next
  • Stretch. A tiny interpret.py that “runs” a recipe against a virtual stub robot — first step of the kitchen simulator (Phase 1).

Success criteria

  • 100% of outputs are schema-valid (Pydantic passes)
  • ≥90% of gold-set steps have correct action + ingredient
  • Every state step has a populated observable
  • A human agrees the JSON is a faithful, executable representation of the recipe

Explicit non-goals (deferred to later phases)

No robot/ROS2 · no camera/vision · no YouTube/video/ASR · no vector DB · no web dashboard · no induction control · no real-time. Each is a later phase; pulling any in now is scope creep.
